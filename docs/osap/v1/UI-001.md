# UI-001 — Diseño de experiencia de usuario (OSAP web)

> Documento de diseño previo a cualquier código React. Define la navegación
> global, cada pantalla y cómo el frontend consume el contrato público de OSAP
> (REST + eventos en tiempo real). Se valida aquí el UX antes de implementar.

Referencias: `docs/osap/v1/api.md` (contrato REST), `docs/osap/v1/frontend.md` (mapeo pantalla→caso
de uso). Toda ruta y nombre de pantalla de este documento se consideran estables
una vez publicados.

---

## 1. Principios de interacción

1. **Nada de polling.** Toda operación larga devuelve un `Job` y el progreso
   llega por el canal de eventos (`WebSocket` / SSE). React no consulta
   `GET /jobs/{id}` en bucle.
2. **Estado = eventos.** La UI es una máquina de estados conducida por los
   eventos del `EventBus`, nunca por estados mutables compartidos.
3. **Acciones largas son deterministas:** cada botón que dispara un Job muestra
   su vida completa (encolado → corriendo → descargando → parseando →
   validando → completado / fallido) con barra de progreso.
4. **Errores visibles y accionables:** fallo ≠ pantalla rota. Se muestra qué
   proveedor/dataset falló y por qué, con opción de reintentar.
5. **Contrato estable:** las rutas, nombres de eventos y campos JSON expuestos
   en este documento no cambian sin versión nueva (`/api/v2`).

## 8. Flujo de eventos en tiempo real

La vida de una resolución viaja por el canal de eventos, no por polling.

```
POST /resolve
   │
   ▼
{ job_id, type: "resolve", state: "running" }        ← 202
   │
   ▼  (WebSocket /api/v1/events/ws)
JobSubmitted ──► JobStarted
                    │
                    ├─► StageStarted (Lookup)   ── Running
                    ├─► StageStarted (Dataset)  ── Downloading
                    ├─► StageStarted (Download) ── Downloading
                    ├─► StageStarted (Parsing)  ── Parsing
                    ├─► StageStarted (Validate) ── Validating
                    │
JobCompleted ──► Completed   (payload: result, progress: 100)
JobFailed    ──► Failed     (payload: error, provider)
JobCancelled ──► Cancelled
```

### 8.1 Contrato de eventos consumidos por la UI

| Evento            | Uso en la UI                                  |
|-------------------|-----------------------------------------------|
| `JobSubmitted`    | Mostrar tarjeta "en cola"                     |
| `JobStarted`      | Marcar "corriendo"                            |
| `StageStarted`    | Avanzar etapa actual (p.ej. "Descargando")    |
| `StageFinished`   | Completar etapa con progreso                  |
| `StageFailed`     | Marcar etapa en rojo                          |
| `JobCompleted`    | Revelar resultado / navegar a detalle         |
| `JobFailed`       | Mostrar error y botón "Reintentar"            |
| `JobCancelled`    | Estado final cancelado                        |
| `DatasetInstalled`/`DatasetUpdated` | Refrescar `/datasets` |
| `LibraryStored`   | Refrescar `/biblioteca`                       |
| `ProviderStarted/Finished/Failed` | Estado de `/proveedores` |

### 8.2 Reducción en el cliente

Cada Job se reduce en un store local (p.ej. `useReducer`/`zustand`):

```ts
type JobState =
  | "pending" | "running" | "downloading" | "parsing"
  | "validating" | "completed" | "failed" | "cancelled";

// stage → estado visible
"Lookup"   → running
"Dataset"  → downloading
"Download" → downloading
"Parsing"  → parsing
"Validate" → validating
```

La UI nunca deriva estado por timing; solo por el último evento recibido.

## 12. Pantalla: Trabajos (`/trabajos`)

`GET /jobs` con suscripción en vivo. Cola + historial.

| Estado     | Acción                          |
|------------|---------------------------------|
| pending    | en cola, autoarranca            |

## 13. Pantalla: Configuración (`/configuracion`)

Preferencias de usuario (`/settings`, `/users`) y del sistema por módulo
(proveedores, pipeline, datasets, cache — ver `docs/osap/v1/api.md`).

- Idioma, formatos preferidos (`UserProfile`).
- Proveedores habilitados y orden.
- Dataset: `cache_dir`, modo (auto/cache/streaming), `num_proc`.
- Pipeline: etapas habilitadas, orden, timeouts.

## 14. Pantalla: Administración (`/admin`)

Operaciones de mantenimiento y observabilidad.

- Salud: `/admin/health-check`, `/monitor`, `/logs`.
- Acciones: `POST /admin/reindex`, `/admin/verify`, `/admin/rebuild-knowledge`,
  `/admin/compact-cache`.
- Cada acción administrativa que tarda lanza un `Job` y reporta por eventos.

---

## 15. Estados transversales

### 15.1 Barra de progreso de un Job

Un componente reutilizable que consume la secuencia de eventos y muestra etapa
actual + porcentaje. Común a Resolver, Descargas, Datasets y Trabajos.

### 15.2 Estados de carga / vacío / error

| Estado  | Comportamiento                                        |
|---------|-------------------------------------------------------|
| Carga   | Skeleton o spinner local; nunca bloquear navegación   |
| Vacío   | Mensaje + CTA (p.ej. "Buscar una obra")                |
| Error   | Mensaje del proveedor/dataset + botón **Reintentar**   |
| Offline | Bandea en `/proveedores`; acciones online deshabilitadas |

---

## 16. Criterios de aceptación del documento

1. Cada pantalla se resuelve 1:1 con casos de uso y recursos del contrato
   (`docs/osap/v1/api.md`, `docs/osap/v1/frontend.md`).
2. Ninguna pantalla requiere polling; todo progreso llega por eventos.
3. Los nombres de sección, rutas y eventos listados aquí quedan congelados.
4. React puede implementarse sin decisiones de UX pendientes.
